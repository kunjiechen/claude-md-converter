# V2 Rendering Fidelity Troubleshooting Plan

## Context

This document records the follow-up investigation plan for fidelity issues found
when rendering:

```text
test/out/G-C110 流程图编制规范_A0.md
test/out/G-C110 流程图编制规范_A0.docx
```

Observed issues:

- Word: images linked from Markdown/raw HTML are not reliably embedded or shown
  at the expected positions.
- PDF: generated output has no table of contents.
- PDF: images are embedded in some places, but placement and sizing are
  visually poor.
- PDF: some images are not embedded or not visible around sections `5.2.4`,
  `6.2.4`, and `6.2.5`.
- PDF: overall visual fidelity is significantly worse than the source document.

The goal of this plan is not to patch a single symptom first. The goal is to
locate the responsible layer in the V2 architecture and build repeatable checks
so future fixes do not regress.

## Current Evidence

Source document characteristics:

- `test/out/G-C110 流程图编制规范_A0.md` has 701 lines.
- The source references 34 files under `test/out/images/media`.
- The source contains many raw HTML image tags, including images inside raw HTML
  tables.
- Sections of interest include:
  - `5.2.4 循环界限`
  - `6.2.4 流线的汇集`
  - `6.2.5 互连`

DOCX package inspection:

- `test/out/G-C110 流程图编制规范_A0.docx` contains 34 files in `word/media/`.
- `word/document.xml` contains 49 drawing references.
- This means the failure is probably not simply "zero images embedded". More
  likely causes are:
  - image relationships exist but are attached to the wrong paragraph/table cell;
  - table-cell raw HTML images are normalized but layout is degraded;
  - images are inserted with a max-width policy that ignores original width and
    table-cell constraints;
  - Word rendering hides/clips images because of table layout, paragraph style,
    or oversized drawings.

PDF evidence:

- The V2 PDF path renders `DocumentModel -> HTML adapter -> PDF backend`.
- With the fixed PDF environment, the default backend is `weasyprint`.
- The generated PDF can embed images, but layout and pagination are still marked
  review for G-C110.
- PDF TOC is not generated by the V2 PDF adapter as a first-class structure.

## Architecture Layers to Check

Use the V2 boundary as the investigation checklist:

```text
Markdown
  -> MarkdownParser AST
  -> DocumentModel
  -> SemanticAnalysis
  -> RenderPolicy
  -> LayoutPlan
  -> RendererAdapter
```

Each issue must be assigned to exactly one primary layer before implementation.

## Rule Change or Code Fix?

These issues must not be treated as "rule-only" problems.

Use this classification:

| Symptom | Primary owner | Why |
| --- | --- | --- |
| Markdown paragraph contains text plus image, but only the image survives | Parser / normalization code | Rules cannot recover content that has already been dropped before `DocumentModel`. |
| Raw HTML block disappears or has no diagnostic | Parser / normalization code | Unsupported content must be explicit before policy can decide how to render it. |
| PDF has no TOC | HTML/PDF adapter code plus policy | `document_policy.toc: required` is already a rule; the adapter must implement it. |
| Raw HTML images appear twice or in the wrong position in PDF | HTML adapter code | The model exposes extracted images for non-HTML targets, but HTML/PDF must avoid duplicating images already preserved in raw HTML. |
| Image size is visually poor | LayoutPlan plus adapter code, then rules | Rules define sizing policy; adapters must convert that policy into CSS/OOXML dimensions. |
| Images in Word table cells are clipped or misplaced | DOCX adapter/table writer code | Word table layout needs cell-aware image sizing and OOXML table constraints. |
| Formal document still looks different after content is present | Rules and CSS/style policies | Once content is preserved, typography, spacing, and print layout can be tuned by rules/styles. |

Short version:

- **Rules** decide what should happen.
- **Parser/normalizer** preserve what exists.
- **LayoutPlan** describes renderer-independent intent.
- **Adapters** must faithfully implement the intent in HTML/DOCX/PDF.

For the G-C110 issues, the first fixes belong to parser and adapters. Rule
tuning comes after content preservation and adapter placement are correct.

## Original Corpus Format Learning

`Original/` is not a DOCX template directory. It is a corpus of compliant
formal documents. V2 must learn and reproduce the format rules; it must not
copy one reference document as a runtime template.

Reference files inspected:

```text
Original/G-C045 软件模块命名规范.docx
Original/G-C046 软件接口命名规范.docx
Original/G-C047 软件命名规范.docx
Original/G-C116 HSI_软件识别号命名规范.docx
Original/G-C119 FC开发指南（C语言）.docx
```

Common format signals:

- Page: A4.
- Margins: top `2.0cm`, bottom `1.5cm`, left `2.0cm`, right `2.0cm`.
- TOC: visible `目录` plus `toc 1..toc 4` entries must be present when the
  formal profile requires a catalogue. A Word TOC field is acceptable only if
  the delivered file also has visible entries or a reliable field-update step.
- TOC title: plain `目录` paragraph, usually not a numbered Heading 1.
- Revision table: first formal table, usually centered, often `Normal Table`.
- Body text: `Normal`, 12pt, Chinese formal font such as 楷体, justified,
  first-line indent about `0.35cm`, line spacing `1.5`.
- Heading styles: Word `Heading 1..4`, not ad-hoc paragraph text.
- TOC styles: `toc 1..toc 4`, left aligned, line spacing `1.0`.
- Table styles: mostly `Table Grid`, revision tables often `Normal Table`;
  tables are commonly centered and Word-autofit is used in many references.
- Code/specification snippets: references use styles such as `规范` or
  `No Spacing`, with compact monospace formatting.
- Image-heavy reference: `G-C119 FC开发指南（C语言）.docx` should be used for
  image layout learning.

V2 defects identified from this comparison:

- V2 used margins that did not match the formal corpus.
- V2 generated `目录` as a numbered heading, which is not compliant.
- V2 TOC depth was too shallow and did not match the common `1-4` corpus
  pattern.
- G-C045 auto profile detection was downgraded to `unknown`, so the effective
  policy became `toc/revision_history/heading_numbering: optional`; the DOCX
  adapter was capable of generating the required structures, but the rules were
  never activated.
- V2 rendered source-exported Markdown TOC entries in addition to generated
  TOC content, causing duplicate catalogue content.
- V2 generated DOCX from a blank document without applying the formal corpus
  style profile.
- V2 table alignment/autofit behavior did not match the corpus baseline.

Fix direction:

- Build a formal DOCX style profile from corpus observations.
- Keep `Original/` as reference evidence only.
- Do not load a reference DOCX as a runtime template unless a future explicit
  product requirement introduces a real template file.

## Fixes Already Applied

Initial fixes made after this investigation:

- Mixed text+image paragraphs are preserved as paragraphs instead of being
  replaced by the first image.
- Raw HTML blocks are preserved as explicit `raw_html` nodes with
  `unsupported_raw_html_block` diagnostics.
- HTML/PDF adapter now emits heading anchors and a TOC when document policy
  requires or recommends TOC.
- HTML/PDF image output now includes CSS sizing constraints so source image
  widths are respected where available and images cannot exceed their container.
- HTML/PDF adapter suppresses duplicate extracted raw-HTML figures when the
  source raw HTML block has already preserved the image at its original
  location.
- DOCX adapter applies a built-in formal style profile learned from
  `Original/*.docx`.
- DOCX adapter uses A4 margins `2.0/1.5/2.0/2.0cm`.
- DOCX TOC title is a plain paragraph, not a numbered heading.
- DOCX now generates visible static TOC entries styled with `toc 1..toc 4`.
  This avoids delivering a blank or placeholder catalogue that depends on Word
  field update behavior.
- DOCX adapter suppresses source-exported Markdown TOC blocks when generating a
  generated TOC.
- DOCX tables are centered and use Word autofit by default.
- Formal naming-spec documents such as G-C045 are detected as
  `automotive_formal_spec` even when the source Markdown does not contain a
  revision-history table.
- The public `Converter(..., pipeline="v2")` path no longer overwrites semantic
  profile detection with the release selector's default profile unless the user
  explicitly supplies `document_profile` or `profile`.
- DOCX table cell text is stripped before insertion; alignment is represented
  through paragraph alignment, not leading spaces or tabs.
- DOCX table cell paragraph direct indents are cleared so body first-line
  indentation does not leak into cells.
- Body `Normal` keeps the reference-style first-line indent of about `0.35cm`;
  table cells and TOC paragraphs explicitly opt out of this indent.

- Generated TOC is visible without requiring Word field update:
  `目录`, `文件修订履历表`, and heading entries are emitted as `toc N`
  paragraphs.
- Table cells are validated to contain no leading spaces, tabs, or full-width
  spaces; cell alignment is applied by DOCX paragraph alignment.
- Table-cell paragraphs are validated to have no direct first-line/left/right
  indent.

## Investigation Sequence

### 1. Source and Asset Inventory

Purpose: prove whether the source references are valid before blaming renderers.

Checks:

- Count all Markdown image references and raw HTML `<img>` tags.
- Resolve every image path relative to `test/out/G-C110 流程图编制规范_A0.md`.
- Record duplicates separately. The document can reference the same image more
  than once.
- Record section ownership for each image, especially `5.2.4`, `6.2.4`,
  `6.2.5`.

Expected artifact:

```text
test/validation-output/g-c110-image-inventory.json
```

Minimum fields:

- `section`
- `line`
- `src`
- `resolved_path`
- `exists`
- `raw_html`
- `inside_table`
- `declared_width`
- `declared_height`

Pass condition:

- Every expected image in source has `exists=true`.
- Missing source assets are listed as source defects, not renderer defects.

### 2. Parser and DocumentModel Preservation

Purpose: prove whether V2 preserves image semantics before renderer adapters.

Checks:

- Compare source image count with:
  - AST image/raw HTML count;
  - `DocumentModel` `ImageRun` and `Figure` count;
  - table-cell `ImageRun` count;
  - `RawHtmlBlock` count.
- For raw HTML tables, verify that `<td><img ...></td>` becomes a table cell
  child image, not only raw text fallback.

Likely failure modes:

- Raw HTML table is preserved as `RawHtmlBlock` but not converted into structured
  `Table` nodes.
- Complex raw HTML blocks duplicate image extraction but lose table location.
- Images inside `<blockquote>`, `<p>`, `<ul>`, or nested HTML table cells lose
  their original structural context.

Pass condition:

- No image disappears between source and DocumentModel.
- Images in sections `5.2.4`, `6.2.4`, and `6.2.5` retain enough context to be
  rendered near the correct section/table.

### 3. Semantic Asset Analysis

Purpose: prove whether image paths are resolved correctly.

Checks:

- For every image, inspect `document.metadata["semantic_analysis"]["assets"]`.
- Confirm `kind == "local_image"` for existing PNG files.
- Confirm `resolved_path` points to `test/out/images/media/...`.
- Confirm repeated references are handled without collapsing location-specific
  layout information.

Likely failure modes:

- Asset resolver keys only by `src`; repeated images share one asset entry.
- Existing assets are marked `unknown_asset` because of path normalization.
- Raw HTML image `src="./images/media/image14.png"` and normalized variants do
  not match exactly.

Pass condition:

- Existing images are `local_image`.
- Missing images produce diagnostics.
- Asset lookup by renderer is deterministic for raw HTML and Markdown images.

### 4. LayoutPlan Image and Table Intent

Purpose: separate "image missing" from "image present but visually wrong".

Checks:

- Inspect `layout_plan.figures` for:
  - source image;
  - resolved status;
  - intended max width;
  - table-cell context;
  - orientation/overflow signals.
- Inspect table layout entries around the problematic sections.
- Verify wide examples in raw HTML tables produce landscape or overflow review
  intent instead of being squeezed silently.

Likely failure modes:

- LayoutPlan has figure-level intent but no table-cell image sizing intent.
- Image max width is global, not constrained by the containing table column.
- Mixed text + image cells do not express vertical alignment, paragraph spacing,
  or cell padding needs.

Pass condition:

- Each problematic image has a layout intent.
- Table-cell images are constrained to their cell width.
- Overflow/landscape risks are explicitly diagnosed.

### 5. Word Adapter Investigation

Purpose: determine whether Word issues are caused by insertion, relationship,
or layout.

Checks:

- Inspect generated `.docx` zip:
  - `word/media/*`
  - `word/_rels/document.xml.rels`
  - `word/document.xml`
- Count:
  - media files;
  - `w:drawing`;
  - `a:blip`;
  - image relationship ids.
- Map each drawing back to the nearest paragraph/table cell text.
- Render the DOCX to PDF/PNG with LibreOffice and inspect pages around
  `5.2.4`, `6.2.4`, and `6.2.5`.

Likely failure modes:

- `DocxImageWriter` uses a global `max_image_width_inches` and ignores original
  raw HTML width/height.
- Images inside raw HTML tables are inserted, but the surrounding table layout
  is not reconstructed.
- Table writer inserts images into cells without preserving the original HTML
  `colgroup` widths, `text-align`, and nested paragraph/list structure.
- Raw HTML fallback text is rendered in addition to extracted images, changing
  spacing and page flow.

Pass condition:

- All images visible at the expected sections.
- Images inside table cells respect cell width and preserve aspect ratio.
- No large placeholder or fallback text distorts the formal document layout.

### 6. PDF Adapter Investigation

Purpose: determine whether PDF issues are HTML adapter issues or backend issues.

Checks:

- Save the intermediate HTML used by the PDF adapter for G-C110.
- Open the HTML directly in a browser.
- Compare:
  - V2 HTML screenshot;
  - WeasyPrint PDF;
  - Chromium PDF, if available;
  - legacy PDF, if available.

Classification:

- If HTML is already wrong, fix `HtmlRendererAdapter` or upstream layout.
- If HTML is right but WeasyPrint PDF is wrong, fix print CSS or backend policy.
- If Chromium and WeasyPrint differ, record backend-specific limitations.

Known PDF issues to verify:

- TOC is missing because V2 PDF does not generate a page-synchronized TOC.
- Image placement is poor because CSS/table/image sizing lacks formal-document
  print rules.
- Some images may be missing if raw HTML table structures are flattened or if
  image paths are not available to the backend `base_url`.

Pass condition:

- PDF includes TOC or explicitly records `toc_not_supported` with fallback
  policy.
- Images in `5.2.4`, `6.2.4`, `6.2.5` are visible.
- Layout is not globally squeezed, clipped, or reordered.

## Fix Order

1. Build the source image inventory and section mapping.
2. Add regression assertions for images in `5.2.4`, `6.2.4`, and `6.2.5`.
3. Fix Word image placement first because DOCX exposes structured relationships
   and is easier to inspect.
4. Save PDF intermediate HTML and classify PDF failures as upstream HTML/layout
   vs backend print CSS.
5. Add TOC support or an explicit PDF diagnostic and rollout limitation.
6. Improve table-cell image sizing and raw HTML table preservation.
7. Re-run visual checks for Word and PDF.

## Acceptance Criteria

Word:

- DOCX package contains all expected media files.
- Every image referenced in the source is visible in the rendered DOCX.
- Images in table cells preserve aspect ratio and fit inside the cell.
- Problem sections `5.2.4`, `6.2.4`, and `6.2.5` visually match the source
  intent.

PDF:

- PDF uses `weasyprint` or another declared high-fidelity backend, not
  `reportlab`.
- PDF contains a TOC, or the missing TOC is an explicit quality-gate blocker.
- Problem-section images are visible.
- Tables and images are not clipped, reordered, or squeezed beyond review
  thresholds.

Quality gate:

- G-C110 cannot be used as evidence for full V2 replacement until Word and PDF
  image fidelity both pass.
- If any formal-document feature remains `review`, legacy fallback must remain
  available for that profile/format.
